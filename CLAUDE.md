# CLAUDE.md — правила работы в репозитории KHORS Desktop

KHORS Desktop — универсальный открытый кроссплатформенный VPN/прокси-клиент (C#, .NET 10, Avalonia). Сначала Windows, затем Linux. Подключается к серверам через внешние ядра Xray-core и sing-box. Лицензия Apache 2.0.

Полное ТЗ: `docs/SPEC.md`. План работ: `ROADMAP.md`. Перед началом задачи сверяйся с обоими; если задача противоречит ТЗ — остановись и спроси.

## Жёсткие правила

1. **Никакого кода из GPL/AGPL-проектов.** Не копируй и не пересказывай построчно код Throne/Nekoray, v2rayN, Hiddify, sing-box, mihomo и других копилефт-проектов. Изучать их поведение, форматы конфигов и документацию — можно; реализацию пишем сами.
2. **Ядра — только внешние процессы.** Никакой линковки с ядрами, загрузки их как библиотек, встраивания их исходников. Взаимодействие: сгенерированный JSON-конфиг → запуск процесса → stdout/stderr → API ядра.
3. **Конфиги ядер генерируются только из внутренней модели профиля** (`Khors.Core`). Не правь JSON ядра строковыми заменами.
4. **UI не требует прав администратора.** Всё привилегированное (TUN, маршруты, WFP, DNS) — только в `Khors.Service` через IPC.
5. **Секреты никогда не попадают в лог** в открытом виде: UUID, пароли, приватные/публичные ключи REALITY, short id, адреса серверов в отчётах. Используй общий маскировщик.
6. **Никакой телеметрии** и сетевых запросов, кроме подписок, проверки обновлений (если включена) и тестов задержки.
7. **Новая зависимость** (NuGet, нативная библиотека, бинарник) — только после проверки лицензии и с записью в `NOTICE`. Если лицензия GPL/AGPL/неизвестна — не добавляй, спроси.
8. **Служба не исполняет произвольное.** Пути к исполняемым файлам ядер, пришедшие из UI, проверяются; служба принимает только команды из `Khors.Ipc`.
9. **Система должна оставаться рабочей.** Любой код, меняющий прокси, маршруты, DNS или WFP, обязан иметь путь отката и вызываться при штатном выходе, при сбое и при следующем запуске.
10. **Платформенный код — только в `Khors.Platform.*`.** `Khors.Core`, `Khors.Engines`, `Khors.Ipc`, `Khors.Service` и `Khors.App` не вызывают API конкретной ОС (реестр, WinINet, WFP, named pipe, P/Invoke, `Microsoft.Win32` и т.п.) и работают с платформой через интерфейсы из `Khors.Platform.Abstractions` (системный прокси, TUN/маршруты, Kill Switch, DNS, служба) и `Khors.Ipc` (IPC-транспорт). Реализация выбирается только в `PlatformComposition.cs` исполняемых `Khors.App` и `Khors.Service`; соблюдение проверяет `tests/Khors.Architecture.Tests`. Подробно — `docs/SPEC.md`, 3.5.
11. **`Khors.Ipc` не завязан на named pipe.** В нём — сообщения, кадрирование и интерфейс транспорта; named pipe (Windows) и Unix-сокет (Linux) — реализации в `Khors.Platform.*`.

## Структура

```
src/Khors.Core               модель, парсеры ссылок/подписок, генераторы конфигов — без зависимостей от ОС и UI
src/Khors.Engines            процессы ядер, логи, API статистики, классификатор ошибок
src/Khors.Platform.Abstractions  интерфейсы платформы: прокси, TUN/маршруты, Kill Switch, DNS, служба
src/Khors.Platform.Windows   реализация для Windows: системный прокси, WFP, маршруты, DNS, хост службы, named pipe
src/Khors.Ipc                контракты UI ↔ служба, кадрирование, интерфейс транспорта
src/Khors.Service            логика привилегированной службы (без API ОС)
src/Khors.App                UI (Avalonia, MVVM на CommunityToolkit.Mvvm)
tests/                       xUnit
tools/cores/                 cores.lock.json и скрипты загрузки ядер
```

## Сборка и тесты

```
dotnet build
dotnet test
dotnet run --project src/Khors.App
```

Работай в нативной Windows-среде (не WSL): TUN, WFP, системный прокси и служба Windows в WSL не проверить. Команды, требующие прав администратора, не запускай сам — опиши, что нужно выполнить, и попроси пользователя.

## Соглашения по коду

- `Nullable` включён, предупреждения — ошибки в `Khors.Core`.
- Асинхронный код с `CancellationToken`; никаких `.Result`/`.Wait()` в UI-потоке.
- Парсеры и генераторы — чистые функции, покрытые тестами. Каждая новая поддерживаемая форма ссылки или подписки добавляется вместе с тестовым вектором в `tests/Khors.Core.Tests/Vectors/` (с вымышленными ключами и адресами).
- Неизвестные параметры при импорте сохраняются в `unknownParams`, а не отбрасываются.
- Тексты UI — через ресурсы (ru, en), без строк в коде.
- Дизайн UI соответствует приложению KHORS для Android: та же палитра и тот же логотип. Цвета — только токены из файла темы `Khors.App`, без литералов цветов в разметке и коде; логотип не перерисовывать «на глаз» — брать исходник от Android-приложения.
- Имена системных объектов на Windows: адаптер `KHORS`, данные пользователя `%APPDATA%\KHORS`, данные службы `%ProgramData%\KHORS`, служба `KhorsService`, фильтры WFP с префиксом `KHORS`.

## Предметные знания

- VLESS + REALITY по умолчанию идёт через Xray-core с fingerprint `chrome`. sing-box не отправляет X25519MLKEM768 в ClientHello REALITY и не подключается к серверам Xray-core 26.9.8+ (`reality verification failed`). Не меняй выбор ядра для REALITY на sing-box без проверки на актуальном сервере.
- В режиме TUN трафик процессов ядер к серверам должен идти мимо туннеля, иначе петля.
- `reality verification failed` означает, что сервер ответил как сайт-маскировка, то есть не принял клиента: неверный ключ/short id/SNI, несовместимый ClientHello или ограничение версии клиента на сервере.

## Как вести работу

- Перед крупным изменением — короткий план и согласование.
- После завершения пункта `ROADMAP.md` — отметить его и кратко записать, что сделано и что отложено.
- Найденные, но не исправленные проблемы — в раздел «Известные проблемы» `ROADMAP.md`, а не молча.
