## Известные проблемы

- В режиме TUN тест задержки неподключённых профилей идёт временными ядрами окна — их трафик тоже попадает в TUN, то есть замер идёт через текущий сервер (задержка завышена). Решение — замер через службу мимо туннеля.
- Режим TUN не проверен вживую с правами SYSTEM (только тесты без прав): проверка — чек-лист 3.2.
- Живая проверка 2026-10-06: в системе остался битый адаптер `KHORS` (sing-box: «create adapter: Cannot create a file when that file already exists. | open existing adapter: Element not found.»). sing-box ждёт его ~15 с и падает, а служба ждала 10 с и убивала ядро молча — пустой лог, «код ?». Исправлено: ожидание старта TUN — 30 с, причина видна в логе и подсказке; после ошибки самого sing-box следующее подключение проходит, поэтому служба при этой ошибке один раз повторяет запуск сама (подключение дольше примерно на 15 с). Не сделано: служба не удаляет битый адаптер сама (нужна очистка через SetupAPI в `Khors.Platform.Windows` перед стартом TUN), а откуда он берётся, не установлено. Принудительное завершение sing-box само его не оставляет (`tun-kill-test.ps1`: три запуска подряд с `Stop-Process -Force` — падает только первый, после перерыва). Следующая проверка: сессия TUN в KHORS 2–3 мин, отключение и сразу `tun-kill-test.ps1` без других программ между ними. Упал первый запуск — виновата остановка сессии службой; прошёл — адаптер портится между сессиями (проверить запуск другого клиента на wintun, например Throne).
- Профиль Main DE (сервер Xray 26.6.28, VLESS REALITY без flow) через Xray 26.9.9 в режиме «Системный прокси»: большинство соединений к серверу висит, хотя другой клиент (на sing-box) работает с тем же сервером на полной скорости. Не проверено: тот же профиль с ядром sing-box в KHORS — покажет, дело ли в ClientHello Xray (`chrome` с X25519MLKEM768).

- WireGuard у части провайдеров (в т.ч. в РФ) блокируется по DPI: рукопожатие не завершается, соединения висят. В режиме `warning` пользователь видит только тайм-аут задержки. Не сделано в 2.7 — подсказка «рукопожатие WireGuard не завершилось — вероятно, провайдер блокирует WireGuard» (признак — нет `received handshake response`; для этого нужен уровень лога sing-box не ниже debug для WireGuard или своя проверка). Обход — AmneziaWG (в sing-box и Xray нет, нужно отдельное ядро — решать отдельно, с проверкой лицензии) или WireGuard поверх другого туннеля (цепочка, после этапа 3). Не объяснено: в логах живой проверки при зависших запросах не было строк `inbound/http … inbound connection`, хотя при локальном воспроизведении неудачного рукопожатия они есть.
- Нет исходников фирменного стиля KHORS Android (палитра светлой/тёмной темы, логотип в SVG). До их получения тема `Khors.App` использует стандартные цвета Fluent; брендовые токены нужно заполнить по Android-приложению (требование — `docs/SPEC.md`, 4.9).
- Правило «частного адреса» Xray (VLESS/Trojan без TLS) воспроизведено приближённо: частные домены (кроме localhost) считаются публичными — такие профили автовыбор отдаёт sing-box, хотя Xray их запустил бы.
- Системный прокси меняется только для подключения LAN; для активных RAS/VPN-подключений Windows (dial-up, встроенный VPN) у WinINet свои настройки — их KHORS пока не трогает.
- Сторож — второй процесс `khors-desktop.exe` без окна; в Диспетчере задач его легко принять за приложение. Отдельный `khors-guard.exe` — вместе с установщиком (5.1).
- Сторож системного прокси — дочерний процесс KHORS: при завершении «дерева процессов» он погибает вместе с KHORS, и прокси возвращается только при следующем запуске. После появления службы (этап 3) откат можно поручить ей.
- `profiles.json` хранит UUID, пароли и ключи открытым текстом (в профиле пользователя, как у других клиентов). Шифрование через DPAPI — решить до релиза.
- Заголовок окна: своя тёмная шапка (И.А); место под системные кнопки окна — фиксированные 150 пикселей справа, без проверки на масштабах 125–200 % и на Linux (там клиентская область может не заходить под заголовок — будет и системный заголовок, и шапка).
- Светлой темы нет: у сайта KHORS только тёмная палитра; при светлой теме Windows приложение остаётся тёмным.
- HTTP-прокси (вход 10809) однажды не работал при живой проверке 2.1 (2026-10-05), SOCKS работал; после пересборки не воспроизводится, при проверке всех профилей работает. Причина не установлена (изменения между сборками HTTP-вход не затрагивали). Кандидаты: браузер переиспользовал соединения после смены прокси/профиля; порт 10809 был занят и выбран другой. Если повторится — записать: после какого действия, какой порт показан в окне, вывод `curl.exe -x http://127.0.0.1:<порт> …`.
- Маскировщик не скрывает домены без порта в свободном тексте (например, `dns: exchanged www.example.com` в логе sing-box) — это адреса назначения, а не серверов. Для отчёта (5.3) решить, маскировать ли историю посещений в логах ядер.
- Память UI: пустое окно Avalonia (Release) — рабочий набор ~134 МБ, приватная память ~93 МБ при требовании ТЗ ≤ 100 МБ (`docs/SPEC.md`, 5). Нужно уточнить метрику в ТЗ и следить за ней по мере роста UI.
- Логотип — квадратная иконка приложения с тёмным фоном (`Assets/logo-512.png`); в круглой кнопке он обрезан по кругу. Для кнопки и шапки нужен вариант без фона из исходников KHORS Android.
