# KHORS Desktop — техническое задание

Версия документа: 0.2 (черновик)
Лицензия проекта: Apache License 2.0

## 1. Назначение

KHORS Desktop — универсальный открытый кроссплатформенный VPN/прокси-клиент. Первая целевая платформа — Windows, следующая — Linux. Он принимает конфигурации любых совместимых серверов (ссылки, подписки, JSON) и подключается к ним через внешние ядра Xray-core и sing-box.

Клиент не привязан к серверам KHORS. Серверы KHORS — лишь один из возможных источников подписки.

### 1.1. Цели

- Подключение к любому серверу с поддерживаемым протоколом без ручного редактирования JSON.
- Корректная работа VLESS + REALITY с актуальными серверами Xray-core (включая 26.9.8+, требующие X25519MLKEM768 в ClientHello).
- Два режима работы: системный прокси и полный туннель (TUN).
- Защита от утечек: Kill Switch, DNS, IPv6.
- Понятный интерфейс для обычного пользователя, подробная диагностика для опытного.

### 1.2. Не цели (на первый релиз)

- Серверная часть, панели управления, биллинг.
- Мобильные платформы (для Android есть отдельное приложение KHORS).
- Linux и macOS в первом релизе: первый релиз — только Windows, но архитектура с самого начала допускает перенос (см. 3.5).
- Собственная реализация протоколов: весь сетевой стек — во внешних ядрах.

## 3. Архитектура

### 3.1. Решения, которые не обсуждаются

1. **Ядра — только внешние процессы.** Никакой линковки, P/Invoke в библиотеки ядер или встраивания их кода. Клиент генерирует конфиг, запускает процесс, читает stdout/stderr и при необходимости API ядра. Это требование лицензионной чистоты (sing-box — GPL-3.0) и надёжности: падение ядра не роняет клиент.
2. **Собственная модель профиля.** Все форматы импорта приводятся к внутренней модели. Конфиги ядер генерируются только из неё и никогда не редактируются «по месту».
3. **UI работает без прав администратора.** Всё, что требует повышенных прав (TUN, маршруты, WFP, системный DNS), выполняет служба.
4. **Никакой телеметрии.** Клиент не отправляет никуда никаких данных, кроме запросов к подпискам и проверок обновлений, явно включённых пользователем.
5. **Платформенный код изолирован.** Код, обращающийся к API конкретной ОС (реестр, WinINet, WFP, маршруты, DNS, службы, named pipe, P/Invoke и т.п.), находится только в проектах `Khors.Platform.*`. `Khors.Core`, `Khors.Engines`, `Khors.Ipc` и `Khors.App` работают с платформой только через интерфейсы (см. 3.5).

### 3.2. Проекты решения

```
src/
  Khors.Core/              модель профиля, парсеры, генераторы конфигов, маршрутизация (без зависимостей от ОС и UI)
  Khors.Engines/           управление процессами ядер, чтение логов, API статистики, классификация ошибок
  Khors.Platform.Abstractions/  интерфейсы платформенных возможностей (без кода, зависящего от ОС)
  Khors.Platform.Windows/  реализация для Windows: системный прокси, WFP, маршруты, DNS, wintun-проверки, хост службы, named pipe
  Khors.Ipc/               контракты сообщений UI ↔ служба, сериализация, абстракция транспорта (без привязки к named pipe)
  Khors.Service/           логика привилегированной службы (без зависимостей от ОС)
  Khors.App/               UI (Avalonia)
tests/
  Khors.Core.Tests/        парсеры и генераторы (основной объём тестов)
  Khors.Engines.Tests/
tools/
  cores/                   скрипты загрузки и проверки ядер (cores.lock.json)
```

### 3.3. Поток подключения

**Режим «Системный прокси»** (без службы):
UI → генератор конфига → ядро (Xray или sing-box) с локальным inbound `mixed`/`socks`+`http` на 127.0.0.1 → UI выставляет системный прокси Windows (WinINet) → при отключении/выходе прокси восстанавливается.

**Режим «TUN»** (через службу):
UI → служба → sing-box поднимает TUN (`auto_route`, `strict_route`, перехват DNS).
- Профиль, требующий Xray (VLESS/REALITY/XHTTP и т.п.): Xray запускается с локальным SOCKS-inbound, sing-box отправляет в него трафик из TUN. Цепочка: TUN(sing-box) → SOCKS 127.0.0.1 → Xray → сервер.
- Профиль, нативный для sing-box: sing-box обрабатывает всё сам.
- Трафик самих процессов ядер к серверу обязан идти мимо TUN (исключения маршрутизации по процессу/адресу сервера), иначе возникает петля.

### 3.4. Выбор ядра

Автоматический, по возможностям, с ручным переопределением в профиле.

| Протокол / транспорт | Ядро по умолчанию |
|---|---|
| VLESS (в т.ч. REALITY, Vision, XHTTP), VMess, Trojan, Shadowsocks | Xray-core |
| Hysteria2, TUIC, AnyTLS, WireGuard | sing-box |
| Возможность, отсутствующая в выбранном ядре | Ошибка с понятным объяснением при сохранении профиля |

Причина выбора Xray для REALITY: sing-box на момент написания не передаёт X25519MLKEM768 в ClientHello REALITY и не может подключаться к серверам Xray-core 26.9.8+ (ошибка `reality verification failed`).

### 3.5. Платформенная абстракция

Платформенные возможности описаны интерфейсами в `Khors.Platform.Abstractions` (интерфейс IPC-транспорта — в `Khors.Ipc`) и реализуются в `Khors.Platform.<ОС>`:

| Возможность | Windows (`Khors.Platform.Windows`) | Linux (`Khors.Platform.Linux`, позже) |
|---|---|---|
| Системный прокси (установка, восстановление, очистка после сбоя) | WinINet / реестр | GNOME (gsettings), KDE (kioslaverc), переменные окружения |
| TUN и маршруты (проверка драйвера, исключения для трафика ядер) | wintun, таблица маршрутизации Windows | /dev/net/tun, `ip route`/netlink |
| Kill Switch | WFP, sublayer KHORS | nftables, таблица `khors` |
| Системный DNS | настройки адаптеров Windows | systemd-resolved / resolv.conf |
| Служба (хост, установка, удаление, статус) | служба Windows `KhorsService` | юнит systemd |
| IPC-транспорт (сервер, клиент, проверка клиента) | named pipe с ACL | Unix-сокет |

Правила:

- Библиотеки `Khors.Core`, `Khors.Engines`, `Khors.Ipc`, `Khors.Platform.Abstractions` не ссылаются на `Khors.Platform.<ОС>` и не используют API конкретной ОС.
- Исполняемые `Khors.App` и `Khors.Service` — точки сборки: они ссылаются на `Khors.Platform.<ОС>`, но обращаются к ней только из одного файла `PlatformComposition.cs` (регистрация зависимостей). Остальной их код пользуется интерфейсами и тоже не вызывает API ОС.
- `Khors.Ipc` описывает сообщения, их кадрирование и интерфейс транспорта (подключённый поток + проверка, что клиент — разрешённый локальный пользователь). Конкретные транспорты — в `Khors.Platform.*`.
- Каждая реализация, меняющая состояние системы, предоставляет откат (см. 4.3) и очистку после сбоя при следующем запуске.
- Соблюдение правил проверяется архитектурным тестом (ссылки между сборками).

## 4. Функциональные требования

### 4.1. Импорт конфигураций

- **Ссылки:** `vless://`, `vmess://` (base64 JSON, формат v2rayN), `trojan://`, `ss://` (SIP002 и legacy), `hysteria2://` / `hy2://`, `tuic://`, `wireguard://`.
- **Подписки:** URL, ответ в формате base64-списка ссылок, простого списка ссылок, Clash/mihomo YAML, sing-box JSON, Xray JSON. Учитывать заголовки `subscription-userinfo` (трафик, срок) и `profile-update-interval`.
- **Источники:** вставка из буфера обмена (одна или много ссылок), файл, QR-код из изображения в буфере обмена или файла, сканирование QR с экрана.
- **Ручное создание и редактирование** профиля в форме.
- **Экспорт:** профиль в ссылку и QR.
- Неизвестные параметры ссылки сохраняются в профиле и показываются как предупреждение, а не отбрасываются молча.

### 4.2. Модель профиля (минимум)

Протокол и его параметры; адрес, порт; транспорт (tcp/raw, ws, grpc, httpupgrade, xhttp, quic); безопасность (none, tls, reality) с SNI, ALPN, fingerprint uTLS, закреплённым сертификатом (`pcs`) и проверкой по имени (`vcn`), REALITY public key, short id, spiderX, ключом ML-DSA-65 (`pqv`), признаком поддержки X25519MLKEM768 сервером (`support-x25519mlkem768`, такие профили — только через Xray); flow; мультиплекс; выбор ядра (auto/xray/singbox); имя, группа, источник (ручной/подписка), дата обновления; служебное поле `unknownParams`. `schemaVersion` хранится в корне файла профилей (миграции — на уровне файла).

Fingerprint по умолчанию для REALITY — `firefox`.

### 4.3. Подключение

- Режимы: «Системный прокси», «TUN». Переключение без перезапуска приложения.
- Один активный профиль; группа «Авто» — выбор по минимальной задержке с периодической перепроверкой.
- Автоподключение при запуске приложения и при входе в систему (по настройке).
- Автопереподключение при падении ядра или смене сети с экспоненциальной задержкой (1, 2, 4… до 60 с).
- Корректное завершение: остановка ядер, восстановление прокси, маршрутов, DNS — в том числе после аварийного завершения UI (служба и сам UI при следующем запуске должны «убирать за собой»).

### 4.4. Маршрутизация

- Пресеты: «Весь трафик через VPN», «Обход для России» (RU-домены и RU-IP напрямую), «Обход локальной сети», «Только выбранные приложения» (TUN).
- Пользовательские правила: домен, суффикс, ключевое слово, IP/CIDR, geosite/geoip, процесс (только TUN). Действия: proxy / direct / block.
- Гео-базы (geoip.dat/geosite.dat или наборы правил sing-box) обновляются по кнопке и по расписанию, с проверкой целостности.

### 4.5. DNS

- Настраиваемый удалённый DNS (DoH/DoT/UDP/TCP) и прямой DNS для обходных правил. Удалённый DNS — в режиме TUN и для WireGuard; адрес в локальной сети опрашивается напрямую, остальные — через сервер. В режиме «Системный прокси» имена сайтов разрешает сервер.
- В режиме TUN — перехват всех DNS-запросов, исключение утечек через системный резолвер.
- Пресеты: Cloudflare, Google, Quad9, AdGuard (DoH и DoT, по IP), свой адрес. По умолчанию — DoH Cloudflare.

### 4.6. Kill Switch

- Реализация на Windows — через Windows Filtering Platform в собственном sublayer KHORS (на Linux — nftables, см. 3.5).
- При включении: блокировать весь исходящий трафик, кроме: loopback, туннельного интерфейса, процессов ядер к адресам серверов, DHCP, локальной сети (по настройке).
- Два режима: «пока подключено» (динамическая сессия WFP — фильтры исчезают при завершении службы) и «постоянный» (фильтры сохраняются до явного отключения пользователем).
- Блокировка IPv6, если туннель его не поддерживает.
- Все фильтры имеют узнаваемое имя «KHORS …» и снимаются командой «Сбросить сетевые настройки KHORS».

### 4.7. Диагностика

- Тест задержки (TCP connect и реальный запрос через прокси), тест скорости.
- Журнал в двух видах: понятный («Подключено», «Сервер не отвечает», «Сервер отклонил подключение») и сырой лог ядер для режима разработчика.
- Классификатор известных ошибок ядер с подсказками. Пример: `reality verification failed` → «Сервер не принял REALITY-рукопожатие. Проверьте публичный ключ, short id, SNI и fingerprint; при использовании sing-box с сервером Xray 26.9.8+ переключите профиль на ядро Xray».
- Кнопка «Собрать отчёт» — архив с логами и конфигами, в которых UUID, пароли, ключи и адреса серверов замаскированы.

### 4.8. Управление ядрами

- В поставке — закреплённые версии официальных сборок Xray-core и sing-box; версии и SHA-256 в `tools/cores/cores.lock.json`.
- Обновление ядер из GitHub Releases по кнопке с проверкой контрольной суммы/подписи; откат на предыдущую версию.
- Возможность указать путь к собственной сборке ядра (для разработчиков и форков).

### 4.9. Интерфейс

- Главное окно: статус и большая кнопка подключения, текущий профиль, режим, задержка, скорость/трафик, время сессии.
- Список профилей с группами и подписками, поиск, сортировка по задержке, флаги стран (по настройке).
- Иконка в трее: подключить/отключить, выбор профиля, режим, выход.
- Языки: русский и английский. Светлая и тёмная тема (по системе).
- Фирменный стиль — как в приложении KHORS для Android: та же цветовая палитра (светлая и тёмная темы) и тот же логотип. Цвета задаются только токенами в одном файле темы, логотип — векторным ресурсом из того же источника, что у Android-приложения; произвольные цвета в разметке не используются.
- Режим разработчика: сырой лог, сгенерированный конфиг ядра (только чтение, с маскировкой).

## 5. Нефункциональные требования

- **Безопасность.** IPC-канал службы (на Windows — named pipe) доступен только локальным интерактивным пользователям; служба принимает только описанные команды и проверяет входные данные (служба не должна позволять запустить произвольный исполняемый файл с правами SYSTEM — путь к ядру из UI проверяется по списку разрешённых каталогов и/или подписи). Секреты в логах маскируются всегда.
- **Надёжность.** Падение UI не оставляет систему без сети. Падение ядра обнаруживается за ≤ 3 с.
- **Производительность.** Холодный старт UI ≤ 2 с; накладные расходы клиента (без ядер) ≤ 100 МБ ОЗУ.
- **Совместимость данных.** Миграции при смене `schemaVersion`; повреждённый файл не приводит к потере всех профилей (резервная копия при записи).
- **Лицензионная чистота.** См. `NOTICE` и раздел 6.

## 6. Лицензирование

- Код проекта — Apache 2.0.
- Запрещено переносить код из проектов под GPL/AGPL (Throne/Nekoray, v2rayN, Hiddify и др.) — даже фрагменты. Изучать поведение и форматы можно.
- Сторонние компоненты поставляются отдельными файлами и перечисляются в `NOTICE` с указанием лицензии и ссылки на исходники. Новая зависимость добавляется только после проверки её лицензии.
- Имена «Xray», «sing-box» и др. используются только для указания совместимости; перед релизом проверить дополнительные условия лицензии sing-box относительно использования названия.

## 7. Критерии приёмки первого релиза (v1.0)

1. Импорт по ссылкам и подпискам всех форматов из 4.1 проходит набор тестовых векторов.
2. Подключение VLESS + REALITY к серверу Xray-core 26.9.9 в режимах «Системный прокси» и «TUN».
3. Подключение Hysteria2 через sing-box в режиме TUN.
4. Kill Switch проходит матрицу: обычное подключение/отключение, падение ядра, kill процесса UI, потеря сети, Wi-Fi ↔ Ethernet, перезагрузка, сон/пробуждение, смена сервера.
5. Тест на утечки DNS и IPv6 в режиме TUN — без утечек.
6. После удаления программы в системе не остаётся фильтров WFP, адаптера, прокси и маршрутов KHORS.
